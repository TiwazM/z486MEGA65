# The x87: speed and accuracy

Part of [z486MEGA65](../README.md). What z486's FPU (`z486/x87/`, upstream commit
62ae68e, "experimental, incomplete x87 support") costs per instruction and
where it differs from a 387/486, measured 2026-11-04 before any change of ours.

On the board, Dr. Hardware gave 26867 Hardstones and 5565 Softstones. Its
DX4-120 has 44617 and 21368, which at 64 MHz would be about 23,800 and 11,400:
the integer side does about 113 % of a 486's work per clock, the FPU about
49 %. Dr. Hardware also called the CPU a "486sx" (possibly CR0.ET, which z486
let software clear as on a 386; on the `fpu` branch it stays 1 as on every
486, z486 a810f48, not yet tried with Dr. Hardware).

The cores with our changes, on the same board (Dr. Hardware's 16-bit System
Performance, Quake's `timedemo demo1`; a dash: not measured):

| Core | Softstones | Hardstones | Quake | CPU named |
|---|---:|---:|---:|---|
| v0.1-preview | 5697 | - | 6.1 fps | 486sx |
| `z486-R6-fpu` (direct loads and stores) | 6890 | - | - | - |
| `z486-R6-fpu2` (+ overlap, exp/log, CR0.ET) | 7155 | - | 7.4 fps | 486dx |
| `z486-R6-fpu3c` (+ FRNDINT, FSCALE, WAIT) | 7420 | 26887 | 7.5 fps | 486dx |
| `z486-R6-fpu4` (+ faster stores) | 7950 | 26896 | 7.6 fps | 486dx |

7950 Softstones are about 70 % of the DX4-120's per clock (49 % before), and
the Hardstones did not move. fpu4 was measured on a second MEGA65 (the same
FPGA and clock).

`CPUSPEED F` (`tools/dos/cpuspeed.s`) times 37 FPU instructions on the board
beside a 486's clocks, for before and after.

## Clocks per instruction

z486's full CPU in Verilator (8 + 8 KB L1, x87 on, as in the core), each loop
hot in the caches, back to back; the 486's from Intel's tables (cache hits).

| Instruction | z486 | 486DX |
|---|---:|---:|
| FLD m32 / m64 / m80 | 4 / **52** / 59 | 3 / 3 / 6 |
| FLD ST(i), FXCH | 3, 3 | 4, 4 |
| FST m32 / m64, FSTP m80 | 22 / **67**, 72 | 7 / 8, 6 |
| FADD, FMUL, FDIV ST,ST(i) | 18, 12, 69 | 8-20, 16, 73 |
| FADD / FMUL m32 | 18 / 13 | 8-20 / 11 |
| FADD / FMUL / FDIV m64 | **60 / 57** / 112 | 8-20 / 14 / 73 |
| FILD m16 / m32 / m64 | 26 / 36 / 52 | 13-16 / 9-12 / 10-18 |
| FIST m16 / m32, FISTP m64 | 39 / 27, 72 | 29-34 / 28-34, 28-34 |
| FCOM ST(1) + FNSTSW AX | 22 | 7 |
| FNSTSW AX, FLDCW, FNSTCW | 14, 24, 16 | 3, 4, 3 |
| FSQRT | 71 | 83-87 |
| FRNDINT, FSCALE, FPREM | **120**, 59, 190 | 21-30, 30-32, 70-138 |
| FSIN / FCOS, FPTAN, FPATAN | 545 / 553, 610, 642 | 257-354, 200-273, 218-303 |
| F2XM1, FYL2X | 17, 18 (a table: see below) | 140-279, 196-329 |

A C double expression (`FLD m64; FMUL m64; FADD m64; FSTP m64`) takes 235
clocks against about 35 on a 486; the same in m32 55 against 31. Integer code
runs on while the FPU works (FDIV followed by up to ~60 ADDs costs no more than
the FDIV).

The arithmetic itself is fast (FMUL 5 clocks, FADD 10, FDIV and FSQRT 62).
The time goes around it:

- **m64, m80 and integer operands** go through the 386's ESC microcode: about
  17 clocks before the command, then the operand as 16-bit words through the
  coprocessor port, about 8 clocks each (31 for an m64). Only m32 and
  register forms have the direct path (`scripts/ucode_optimize.py:253-282`,
  `hardwired_control.sv:80`, `x87/x87_unit.sv:211-239`), which carries one
  32-bit operand.
- **6-8 clocks per operation** of bridge register, command ROM, start and a
  3-clock retire, one operation at a time (`x87_control.sv:745-761`, 794,
  1308, 1446); only one command waits in the bridge.
- **FST m32** rounds and packs in the executor and comes back through the
  bridge (22 clocks).
- **FNSTSW, FLDCW, FNSTCW, FWAIT** go through the 386 microcode and the port.
- **FRNDINT and FSCALE** shift one bit per clock; FRNDINT is most of FPREM's
  time. FSIN's 46 executor steps wait about 5.7 clocks each on the
  polynomial sequencer (`x87_control.sv:1729-1800`).

## Accuracy

Every 387 instruction decodes (`x87/build_x87_command_decode.py`), and 80-bit
loads, stores and register copies keep all their bits. The gaps, most
important first (found with a test bench on `x87_control` against exact
references):

1. ~~**F2XM1, FYL2X, FYL2XP1** came from a 257-entry table with linear
   interpolation: 4-5 digits. log2(1.001) was 1 % off, 2^x - 1 for x = 1e-5
   was 0, FYL2X of +inf or a NaN returned 16384, FYL2X(0) gave an invalid
   operation instead of -inf.~~ Fixed on the `fpu` branch (Done, below).
2. **FPREM, FPREM1** divide, multiply and subtract at 53 bits instead of a
   partial remainder (`x87_control.sv:1641-1690`): fmod(1e20, pi) = 0, some
   results with the wrong sign and quotient bits; C2 is never set, so
   libraries that loop on it stop after one pass.
3. **53 bits outside the registers.** Arithmetic and conversions use a 53-bit
   significand (`x87_pkg.sv:16`): FILD m64 cuts (2^63 - 1 -> 2^63 - 1024),
   FISTP m64 and FRNDINT lose the low bits, FBLD/FBSTP keep about 16 of 18
   digits, precision control 64 works as 53. FILD/FISTP qword used as an
   8-byte copy, Pascal's Comp and BCD accounting break.
4. **Range:** a multiply's exponent wraps (2^12000 * 2^12000 is tiny, no
   overflow, `x87_executor.sv:1645`); ~~FSCALE sets no overflow or
   underflow~~ (fixed on the `fpu` branch); a divide's underflow flushes to 0; the denormal flag only on DIV, SQRT and
   the transcendentals.
5. **FSIN, FCOS, FPTAN** reduce with a 33-bit pi/2 (`build_x87_poly.py:58`):
   fine to about 1e7, sin(1e15) 3.5 % off, sin(1e18) above 1.
6. Unnormals, pseudo-NaNs and pseudo-infinities count as numbers (a 387:
   invalid operation); with precision, overflow or underflow unmasked the
   result is dropped instead of stored; FXCH with an empty register loses the
   other one; FINCSTP/FDECSTP leave C1; FLDENV/FRSTOR take the tag word as it
   is.

### Berkeley TestFloat

`make test-x87-testfloat80` in z486's `tests/` (z486 `fpu` 73b8ee4) runs
TestFloat 3e's level-1 cases through the executor in the x87's formats,
operands as the register stack hands them over, and lets `testfloat_ver`
judge results and flags. These are the shares of cases that differ, over
all four rounding modes (46,464 cases per mode for the two-operand
functions, 159-912 for the others):

| Operation | Operands that fit 53 bits, PC 53 | All 64-bit operands, PC 53 | PC 64 |
|---|---:|---:|---:|
| FADD, FSUB | 0.4 % | 34 % | 83 % |
| FMUL | 10 % | 21 % | 86 % |
| FDIV | 3.4 % | 47 % | 82 % |
| FSQRT | 0.6 % | 16 % | 47 % |
| FRNDINT | 0 | 24 % | |
| FCOM, FUCOM (all six relations) | 0 | 0.1 % | |
| FST m32, m64 | 0 | 0.2 % | |
| FIST m32 / FISTP m64 | 0 / 0 | 0 / 2.7 % | |
| FLD m32, m64, FILD m32 | 0 | | |
| FILD m64 | | 18 % | |

At PC 24 the 53-bit operands fail 2.8 % (FADD), 10 % (FMUL), 5.7 % (FDIV),
0.6 % (FSQRT). Every failure with operands and results in the normal range
is gap 3 (64-bit operands taken as 53 bits plus guard/round/sticky, so
results lose low bits or the inexact flag); with 53-bit operands what
fails is all at the edges of the range:

- FMUL's exponent wraps: products that should underflow come out huge,
  products that should overflow come out tiny (most of FMUL's 10 %).
- An overflow gives infinity in every rounding mode (round down, up or
  toward zero must give the largest finite number away from the
  direction), without OE or PE (FADD, FSUB, FMUL).
- FDIV flushes an underflowing quotient to zero instead of a denormal.
- Denormal operands (below 2^-16382): FADD/FSUB results a bit off or NaN,
  FDIV and FSQRT wrong values.
- Underflow is detected before rounding: FST m32/m64 of a number that
  rounds up to the smallest normal sets UE, which Intel's x87 does not
  (it detects tininess after rounding).
- FISTP m64 of -2^63-1 gives -2^63 with PE instead of the invalid
  operation (gap 3).

What works: unmasked exceptions reach the PC (ES, FERR# to IRQ13 and port
F0h, or INT 16 with CR0.NE), stack faults, NaNs, signed zeros, FSQRT, FPATAN,
FXAM, the constants (64-bit, rounded as RC says). z486's own x87 tests pass;
they check only values that come out exact at 53 bits or at table points.

## Done

- **Direct loads** (z486 `fpu` branch, 2026-11-04): m64, m80 and m16 loads
  read their operand with the microcode's own RD words (overlays at A00-A1D,
  `scripts/ucode_optimize.py`) and hand it to the x87 in one go, without the
  386 routine's port transfers; FILD m32 and the DA forms join the m32 path.
  Each part is limit-checked and translated on its own, and the x87 sees
  nothing until all of it is in. Also fixed on the way: a hang when FLDCW
  unmasked an exception right before an FLD m32, 16-bit code's m32 reads
  checked as two bytes, FNSTENV's operand pointer after a direct load.
  `x87_direct_loads`, `x87_direct_load_faults`, `x87_direct_load_fallback`
  test it (values, splits, page and limit faults, #NM, pending errors).

  | Instruction | Before | After | 486DX |
  |---|---:|---:|---:|
  | FLD m64 / m80 | 52 / 59 | **10 / 12** | 3 / 6 |
  | FADD / FMUL / FDIV m64 | 60 / 57 / 112 | **24 / 19 / 76** | 8-20 / 14 / 73 |
  | FILD m16 / m32 / m64 | 26 / 36 / 52 | **10 / 9 / 11** | 13-16 / 9-12 / 10-18 |
  | FCOMP m64 + FNSTSW AX | 76 | **39** | 7 |

  The microcode ROM grows from 2560 to 3072 words.

- **Direct stores and status words** (the same branch): m64, m80 and m16
  stores (FST/FSTP m64, FISTP m64, FSTP m80, FBSTP, FIST/FISTP m16, and m32
  stores in 16-bit code too) check their whole destination for writing first
  (CW words), then post the command and write the x87's result parts with
  WR words, taken straight from its transfer queue instead of data port
  reads; nothing after the command can fault, so a faulting FSTP never pops.
  A store behind a posted port write waits instead of falling back. FNSTSW
  AX, FNSTSW m16 and FNSTCW wait until every earlier x87 instruction has
  finished and take the word without the port; FLDCW is a direct m16 load.
  Also fixed: a CW split over two pages checked only the first one when it
  hit in the TLB (an FSTP dword over an absent page popped and wrote half
  before its page fault), and an x87 instruction issued beside a MOV CR0,
  CLTS or LMSW decided on the old TS/EM (`mov cr0` setting TS, then `fstp
  tword`, skipped #NM). `x87_direct_stores`, `x87_direct_store_faults`,
  `x87_direct_store_fallback` and `x87_status_after` (FNSTSW right behind
  loads, compares, arithmetic and stores) test it.

  | Instruction | Before | After | 486DX |
  |---|---:|---:|---:|
  | FST m32 / FST m64 / FSTP m80 | 22 / 67 / 72 | **20 / 26 / 26** | 7 / 8 / 6 |
  | FIST m16 / FISTP m64 | 39 / 75 | **25 / 36** | 29-34 / 28-34 |
  | FNSTSW AX, FLDCW, FNSTCW | 14, 24, 16 | **4, 8, 5** | 3, 4, 3 |
  | FCOM ST(1) + FNSTSW AX | 22 | **11** | 7 |
  | FCOMP m64 + FNSTSW AX | 39 | **26** | 7 |
  | C float-to-int (FLD ST, FNSTCW, FLDCW, FISTP m32, FLDCW) | 121 | **50** | 44-49 |

  The C double expression (`FLD m64; FMUL m64; FADD m64; FSTP m64`) now
  takes 79 clocks, from 235 at the start.

- **Overlap and a shorter retire** (z486 `fpu` 74acd11): results and pushes
  are written to the stack in the cycle they complete; with every exception
  masked, the next register command or direct load or memory operation is
  taken while a plain operation (arithmetic, compare, FSQRT, FRNDINT) runs,
  reads its registers as they will be, and starts the cycle the result is
  written; a register instruction behind it waits in the CPU instead of
  falling back to the 386 routine when the wait is short (at most about 130
  clocks; an interrupt then comes after the instruction, not before). The
  polynomial engine fetches the next program step while one runs. Normal
  m64 operands are extended without the executor. `x87_overlap` runs every
  sequence with and without overlap and compares the FSAVE images;
  `x87_reg_wait_irq` checks interrupts during the waits.

  | Instruction | Before | After | 486DX |
  |---|---:|---:|---:|
  | FADD / FMUL / FDIV ST,ST(i) | 18 / 12 / 69 | **11.6 / 6.5 / 64** | 8-20 / 16 / 73 |
  | FADD / FMUL m64 | 24 / 19 | **13.6 / 10** | 8-20 / 14 |
  | FCHS, FABS, FLD1, FLDZ | 5 | **3** | 6, 3, 4, 4 |
  | FSQRT | 71 | **66** | 83-87 |
  | FSIN, FPTAN, FPATAN | 545, 610, 642 | **344, 408, 466** | 257-354, 200-273, 218-303 |
  | C double expression | 79 | **61** | about 35 |

- **Exp and log** (z486 `fpu` 2d424f5): F2XM1, FYL2X and FYL2XP1 run as
  programs on the polynomial engine, as FSIN does, instead of the table:
  fdlibm's expm1 (2^x - 1 = expm1(x ln 2), ln 2 in two parts), log (the
  operand split into exponent and mantissa by a new engine step) and log1p
  (FYL2XP1 never forms 1 + x), with the multiply by y kept exact in parts.
  Worst error against mpmath at 53 bits, over 60,000 cases per region:
  0.98 ulp (F2XM1), 0.68 (FYL2X), 0.65 (FYL2XP1), from 4-5 digits before.
  Zeros, infinities, NaNs, negative and denormal operands follow Intel's
  tables (log of 0 is -inf with ZE, log of a negative is invalid).
  `x87_trans_logexp` checks 200 random and edge cases bit for bit and 110
  special cases with their flags. The engine's program ROM is now 256 words
  and its constant table 128.

  | Instruction | Before | After | 486DX |
  |---|---:|---:|---:|
  | F2XM1 | 17 | **271** | 140-279 |
  | FYL2X | 16 | **459** | 196-329 |
  | FYL2XP1 | 29 | **376** | 171-326 |

  Right instead of fast: FYL2X and FYL2XP1 are slower than a 486 (FYL2X's
  22 additions, one divide). Still open there: results below 2^-16382
  flush to zero instead of denormals, and the FMUL range gap (4) applies
  within about 2^40 of the exponent limits.

- **FRNDINT, FSCALE and WAIT** (z486 `fpu` dc48781): FRNDINT rounds by a
  mask chosen from the exponent (3 executor steps instead of a shift loop
  of up to 110); FSCALE is an executor operation, an exponent add with
  Intel's special cases and now overflow and underflow (largest finite or
  infinity per RC, denormal or zero, OE/UE/PE). FPREM/FPREM1 and the
  polynomial engine's reduction use the same rounding. WAIT (9B) has its
  own overlay: it completes at once when the FPU has finished everything it
  accepted (held commands included) and no exception is pending, holds in
  place while the FPU works (an interrupt then comes after it), and leaves
  #NM, an unmasked exception and a long wait to the 386 routine as before.
  `x87_frndint`, `x87_fscale`, `x87_fprem` (exact references), `x87_wait`,
  `x87_wait_errors`, `x87_wait_irq` and `x87_wait32` test it.

  | Instruction | Before | After | 486DX |
  |---|---:|---:|---:|
  | FRNDINT | 114.5 | **7.5** | 21-30 |
  | FSCALE | 59 | **6** | 30-32 |
  | FPREM | 185 | **92** | 70-138 |
  | FWAIT (FPU idle) | 6 | **2** | 1-3 |
  | WAIT + FADD, WAIT + FMUL (16-bit compiler style, pairs) | 35.5, 25.5 | **32, 24** | |

  A WAIT now waits for queued work the 386 routine's BUSY# poll did not
  see: WAIT-prefixed FLD/FMUL/FADD/FSTP m64 takes 91 clocks instead of 79.

- **Faster stores** (z486 `fpu` 8308c00, fe56218): FST/FSTP m32 and m64 of a normal
  value whose result is a normal of the format, a zero or an infinity are
  rounded and packed in one step in the store set-up (`x87_fast_fst`)
  instead of the executor's four; denormal results, overflow, NaNs and an
  empty register still take the executor. A direct store takes its result
  whole in one cycle instead of 32 bits at a time through the transfer
  queue. And an FST/FSTP m32/m64 or FSTP m80 is packed while the CPU still
  checks its destination: from the issue, with the FPU idle, control reads
  ST0 and packs it without changing anything; the store word ends as soon
  as its command is accepted, and the command only pops and sets PE and C1,
  its value dropped. A fault in the checks still leaves the FPU untouched.
  TestFloat (levels 1 and 2, every rounding mode): the one-step conversion
  agrees with the executor's in value, PE and C1 on all 236,643 cases it
  takes. Also fixed: PEREQ dropped for a clock between a store's set-up and
  its first result word, and the 386 routine (a store with an unmasked
  exception pending) could sample it there and skip its data reads.

  | Instruction | Before | After | 486DX |
  |---|---:|---:|---:|
  | FST m32 / FST m64 / FSTP m80 | 19 / 25 / 26 | **8 / 13 / 19** | 7 / 8 / 6 |
  | FIST m16 / FISTP m64 | 24 / 33 | **23 / 31** | 29-34 / 28-34 |
  | C double expression (`FLD m64; FMUL m64; FADD m64; FSTP m64`) | 61 | **53** | about 35 |
  | The same in m32 | 43 | **36** | about 31 |

  FSTP m80 is now mostly the CPU's own words: three destination checks and
  three writes, each with its delay slot. Behind arithmetic a store waits
  for the result, as on a 486, so the expressions gain less.

## What to do, in order

1. ~~Direct loads~~ and ~~stores~~ (above).
2. ~~FNSTSW AX, FLDCW and FNSTCW without the port~~ (above).
3. ~~A shorter retire and the next command taken meanwhile~~ (above). FXCH and
   FLD ST(i) are still 3 clocks: the CPU's overlay itself takes 3.
4. ~~FST m32 packed in one step~~ and ~~FRNDINT and FSCALE by masks and a
   barrel shifter~~ (above). FYL2X, F2XM1 and FPTAN (about twice a 486) are
   the slowest now; FSTP m80 (19 clocks, a 486 6) would want fewer CPU
   words.
5. Accuracy: ~~log2/exp2 on the polynomial engine~~ (above; FYL2X and
   FYL2XP1 still want speed), an exact FPREM loop, exact int64 and BCD paths
   beside the 53-bit datapath; then the range edges TestFloat shows (FMUL's
   exponent wrap, overflow in the directed rounding modes, FDIV's underflow,
   denormal operands) and 6.

A full 64-bit significand would grow the multiplier, which is already the
slowest path of the build at 64 MHz (`mul_p00` into `work_r`, +0.436 ns):
last, if at all. All of it is in z486 itself, so it wants a fork of z486 (or
patches nand2mario takes upstream), not `tools/z486_sources.py`'s small
patches.
